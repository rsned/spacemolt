**QUEUED IDEA 2026-07-23 (user, needs brainstorm). Marketbots scan freight demand: turn the idle marketbot fleet into a distributed freight-contract sensor net.**

**Why it works (CONFIRMED):** The freight board is **docked-only / station-scoped** — `ShippingList fetches the current station's freight board (docked-only)` (`pkg/game/mcp_game_client_commands.go:2009`); contracts carry `OriginBaseID` (`pkg/game/serverapi/responses_shipping.go:26`, `ShippingListResponse` = "the docked freight board" :148). So a lone mobile trucker only ever sees the board where it currently sits. The ~35 marketbots are already parked idle across ~40 stations ([[reference_haul_fleet_capacity_ceiling]], [[project_idle_mining_marketbots]]) → each can `shipping list` its LOCAL board and report → aggregate a universe-wide freight-demand map no single hauler can build.

**Payoff (user framing):** the mission/freight fleet then routes DELIBERATELY to stations with known acceptable contracts instead of "chaotically travelling around hoping for a shipping." Compounds with [[project_freight_probation_bootstrap]] — a probationary carrier can head straight to a station known to hold an acceptable starter contract rather than burning fuel hunting a dry board.

**Design opens (brainstorm):** where the demand map lives (shared KB table, like the haul scanner's opportunity store — see [[project_scanner_outage_expiry_fix]]); freshness/expiry of scanned contracts (they get accepted/expire); do marketbots add a `shipping list` to their idle loop (they're docked already — near-free) or a dedicated scan role; how the mission fleet consumes it (route selection in play_as/worker planner). Mirrors the existing haul arbitrage-scanner pattern but for freight contracts + leverages already-distributed workers instead of one scanner.

**⚠️ NEEDS-RETHINK (LIVE OBSERVATION 2026-07-23):** a real `shipping --action=list` from a probationary carrier returned `"shipments": [], "total": 0` with `empty_reason_code: "no_eligible_shipments"` / `"trusted cargo requires trusted carrier standing"`. So the board **filters OUT contracts the caller can't accept** rather than listing them with an `Eligible=false` overlay — i.e. a low-tier marketbot scan does NOT reveal higher-tier demand; it under-reports to the scanner's own standing. The `ShippingListing.Eligible/Reason` overlay fields (line below) evidently apply only to contracts that clear a coarser gate, not to the full station board. **Consequence:** a single-tier marketbot sensor net has a blind spot for all tiers above it. Options for the brainstorm: (a) wait for the dev team's forthcoming server-side "all contracts" / active listing [[reference_shipping_no_active_contracts_listing]]; (b) accept demand-map coverage only up to marketbot tier; (c) diversify scanner tiers. Re-validate the "all carriers see the same board" assumption before building.

**RESOLUTION (user, 2026-07-23):** option (c) — **certify marketbots up the carrier ladder ONE AT A TIME** so the sensor net keeps a scanner at each tier (probationary→licensed→trusted→prime). Reuse the existing [[project_freight_probation_bootstrap]] mechanism (bounded loss-leader deliveries) to climb; a trusted-certified marketbot then SEES and reports trusted-tier demand the probationary ones can't. One-at-a-time bounds the bootstrap cost and keeps the rest of the fleet station-parked. Bonus: each certified marketbot is also an extra earning carrier. **Backfill the vacated post:** an elected marketbot leaves its station to run certification deliveries, so its market-watch coverage must be handed to ANOTHER agent (spare/idle slot takes over the market-watcher role at that station) while it's out — hand back on return, or keep the swap permanent. Design opens: which marketbot(s) to elect, how far to climb, whether certified scanners still idle-park between scans, and the backfill/handback mechanism (overmind role reassignment — relates to [[project_ship_role_naming_scheme]] / [[project_generalist_agent_selector]]).

**LABOR POOL (user, 2026-07-23):** the mission-learn fleet has ~20-30 mostly-idle agents (the same idleness the probation bootstrap is unsticking) — use THEM for both roles, no new agents needed: elect some to climb the carrier ladder as per-tier scanners, use others to backfill vacated market-watch posts. Turns the fleet's idle capacity into freight-demand sensing + tier coverage.

**SCOPE BOUNDARY (user, 2026-07-23 — important):** This works for FREIGHT contracts only, NOT missions. **Missions (`get_missions`) are AGENT-SPECIFIC views** — each agent sees a different SET gated by its own skills/reputation/faction, so a marketbot literally cannot preview what engineer-2 would see. Freight is different: the shipping board is STATION-level content (all carriers docked there see the same contracts) with a per-actor eligibility OVERLAY — `ShippingListing.Eligible bool` + `Reason` + `ReputationEligible bool` (`responses_shipping.go:60,67-73`) says whether THIS carrier can accept it. So a marketbot scan yields the shareable DEMAND signal (contract exists + reward + origin/dest/route), NOT eligibility (which is per-actor). Consequence for the design: freight-demand map decides WHERE to send a worker; the per-agent MISSION check stays per-agent, done by that worker itself when docked ("stay per agent when docked to see if anything viable is there"). The two complement, don't overlap.

Two fleet features built 2026-06-28 (working tree, **not committed**, not yet deployed).

## 1. Faction treasury buffer (`pkg/worker/treasury.go`)
- `depositProfitShare()` deposits `floor(5% × profit)` to the player's faction treasury; gated on `state.Player.FactionID != ""` and cut ≥ 1cr. Hooked into `recordHaulResult()` in haul.go (RealizedProfit) and into shuttle delivery (booked fare).
- `treasuryRescue.maybe()`: when an idle, faction-member worker is **< 1,000 cr**, pull a **5,000 cr** injection, **max once/hour** (cooldown advances on every attempt, incl. failures, so un-permissioned agents don't hammer). Held on `WorkerDispatch.treasury` so the cooldown survives across idle passes; threaded into HaulDeps/ShuttleDeps. Called at the idle/empty-hold point of Haul() and Shuttle().
- Client methods `FactionDepositCredits/FactionWithdrawCredits` already existed. **Withdraws need `manage_treasury` permission** (deposits don't) — without it the withdraw errors harmlessly and the agent idles. [[reference_login_vs_reconnect_gating]] unrelated; this is faction perms.
- Narrowed to a 3-method `treasuryClient` interface for testability (same pattern as nudgeReconnect). Tests: `treasury_test.go`.

## 2. Shuttle role — passenger taxi (`pkg/worker/shuttle.go`)
- New standing behavior, mirrors hauler. Loop: ensure docked → treasury rescue → `ListStationPassengers("")` → rank destinations → `LoadPassenger(station)` (boards ALL waiting for that dest that fit) → `Autopilot(system, station)` → `Dock` (auto-delivers + collects fares) → deposit 5% → refuel → repeat.
- **Real API** (singular): `load_passenger {destination: <station_id>}`; arrivals auto-deliver on dock via `passenger_arrivals.fare_collected`. Trust `LoadPassengerResponse.Count/TotalFare` (berth/class limits board fewer than waiting; first-class won't downgrade).
- **Stronghold exclusion**: drops destinations whose `destination_system` has `is_stronghold` in the KB systems table (ships get destroyed flying to pirate strongholds). Also drops unreachable / > `DefaultShuttleMaxJumps` (8). Ranks by total estimated fare desc; tries top `shuttleLoadAttempts` (3) until one boards.
- Added typed client methods `ListStationPassengers`/`LoadPassenger` (+serverapi `StationPassenger`/`ListStationPassengersResponse`/`LoadedPassenger`/`LoadPassengerResponse`) in `pkg/game/client_passengers.go`. **Interface change broke 3 mocks** (MCPGameClient real impl + pkg/agent & pkg/skills test mocks) — all updated. [[feedback_gameclient_interface_mocks]]
- Wiring: `dispatch.go` supported+case, `data/scripts/shuttle.smolt`, `roles.yaml` shuttle role. Tests: `shuttle_test.go` (ranking: stronghold/budget/fare/unknown-system).

## ROOT CAUSE CONFIRMED 2026-06-28 — it's the BERTHS (both prior theories were WRONG)
The earlier "losing to contention" (line 27) and "no demand / broken lookup" (canary verdict) conclusions are BOTH WRONG. Controlled play_as test on `craftsman-1` docked at Haven Grand Exchange settled it:
- `list_station_passengers` (NO params = the shuttle's exact empty-station call) → **WORKS**, returned the live 15-passenger queue. Lookup is fine.

- **Berth facts:** hulls have ZERO native passenger berths — they come only from utility-slot MODULES: Economy Passenger Cabin = **12** berths, Business Cabin = **6**, First-Class Suite = **3** (per `data/game-api/latest/catalog_items.json`). johnny_cab carries ONLY the First-Class Suite. Failure log = **567** `0 boarded (taken by another, or no matching free berth)` + **107** `nobody fit (berth/class limits)` out of ~1300 result lines; only 235 were genuinely "no passengers waiting."
- **RESOLVED 2026-06-28 — berth-class is NOT the blocker.** craftsman-1 `list_passengers` = `eco 0, biz 0, first 3` (only a First-Class Suite) yet carries **Priko Mantu [business]** in a first berth. **Seating rule (user-confirmed):** every passenger takes the HIGHEST available berth; no passenger takes a berth BELOW their class. ⇒ a **first berth seats ANY class**, a **business berth seats business+economy**, an **economy berth seats economy only**. So johnny_cab's 3 first berths can carry ANY 3 passengers. The real limiters are: (1) **berth COUNT = 3/trip** (throughput), and (2) **the list→load contention gap** — `load_passenger` runs "on next tick" (~10s), so other ships grab the passengers in between. Over 567 attempts at a populated hub, 0 boards smells like MORE than contention → suspect a **worker targeting/timing bug** in shuttle.go's list→rank→load sequence (ranks destinations from one list, then loads a tick later against possibly-emptied destinations), since craftsman-1's MANUAL `load_passenger <dest>` boarded instantly.
- **Loadout note:** because economy berths seat economy-only and "highest available" is greedy, a volume refit wants a queue-matched mix (lots of economy for the bulk, some business/first); naively mixing first+economy lets economy pax cannibalize premium berths.
- **Code audit 2026-06-28 (`pkg/worker/shuttle.go`):** NO berth-class pre-filter in current source — the 107 `nobody fit (berth/class limits)` log lines are from an OLDER binary johnny_cab still runs; current code only emits `0 boarded (taken by another, or no matching free berth)`. `rankShuttleDestinations` groups waiting pax by destination, drops strongholds/unreachable/`>maxJumps` (DefaultShuttleMaxJumps=**40**, not 8), sorts by **total fare desc**. Load loop tries only the **top `shuttleLoadAttempts`=6** of ~13 destinations → the 7 lowest-fare destinations are NEVER attempted. `load_passenger` is tick-deferred (~8s). **CONTENTION CONFIRMED 2026-06-29 (natural experiment):** Grand Exchange queue dropped **15 → 2 in ~3h** — other ships boarded 13. Demand is real and gets consumed, just not by johnny_cab. The 2 that lingered: 1 NEW easy business fare (Goro→Cargo Lanes, 1062, 2 jumps) + Abbess Thorne→**Crix Stronghold** (Bellatrix, 13260) which persists *because it's a stronghold trap every ship correctly refuses* (that's why the fattest fare never clears). **ROOT CAUSE = presence + targeting, NOT berths/lookup/demand:** (1) johnny_cab spends most time WANDERING (Cargo Lanes/Gold Run), not even present at the hub to compete; (2) when present it chases TOP-FARE destinations — the ones every ship grabs first — loses the ~8s tick-deferred load race, and trying only top-6 never falls through to winnable cheaper fares. **FIX (behavioral, in `pkg/worker/shuttle.go`):** (a) CAMP at high-demand hubs — kill/raise the eager `shuttleRepositionThreshold=2`; presence is half the battle; (b) try ALL reachable ranked destinations per pass, not just `shuttleLoadAttempts=6`; (c) rank by win-probability (cheap/near/less-contested) not pure fare; (d) berth/hull throughput is a SECONDARY lever; (e) the marketbot passenger-demand survey [[project_passenger_demand_intel]] tells it which hub has the most uncontested demand. ## ★ TRUE ROOT CAUSE FOUND 2026-06-29 — DEADLOCK from undelivered passengers (NOT the targeting fix)
The camp+try-all fix did NOT fix earnings because the real bug is a **delivery deadlock**. `list_passengers` on johnny_cab showed **3 passengers ABOARD, all 3 first berths full** (eco 0/biz 0/first 3 used), bound for Crimson War Citadel (2, first, 351t left) + Ironhearth Station (1, business, 532t). Berths full ⇒ every `load_passenger` returns 0 ("no free berth") AND no fare ever collects (never delivered) ⇒ 0 boards + 0 credits, exactly the symptom. THREE contributing factors:
1. **No re-delivery of aboard passengers**: `Shuttle()` boards-then-delivers in ONE pass; it never re-attempts delivery of passengers already aboard from a prior pass. So any interrupted/failed delivery strands them permanently.
2. **My shuttle restart (~01:36) caught it mid-delivery** — passengers stayed aboard server-side; the fresh worker never resumed the delivery → deadlock.
3. **Station-id ALIASES (legacy data)**: one physical station has multiple ids — Sol = `sol_central`/`sol_base`/`confederacy_central_command`; Krynn = `war_citadel`/`crimson_war_citadel` (KB pois only has the canonical `sol_central`/`war_citadel`; the alias rows don't exist). Passengers carry the ALIAS id (`crimson_war_citadel`), so the worker's delivery routing can't resolve it against the KB → can't navigate → contributes to the failed delivery. (Manual dock at the physical station still delivers — server matches on the real station.)

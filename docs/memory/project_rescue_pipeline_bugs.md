**Incident (2026-07-16 12:34 → fixed manually 2026-07-17 ~02:45):** salvager-3 + trader-10 quarantined 13h at Distant Light. Full writeup context: haulers routed to mobile_capital, which MOVED to unknown_edge; worker loops on "It's called a Mobile Capital for a reason — it's not here right now" without handling it; stall-watchdog quarantined (correct) and queued rescues.

**NEW BUG (2026-07-19, fighter-4): rescued worker never sees the fuel — client state not refreshed.** assist-sol transferred +77 fuel to fighter-4 (server-side 3→80, operator-confirmed via play_as `"fuel":80`), rescue record went `done`. But fighter-4's WORKER kept its cached `fuel=3`, so its client-side pre-jump fuel guard blocked it from ever *attempting* the jump — it spun on "Route found" queries for 20+ min, still fuel=3 in status. The rescue succeeded server-side but was silently ineffective because the strandee didn't re-fetch ship state. Distinct from the fuel-dead-UNDOCKED case (those keep re-issuing the jump command, which the server accepts on real fuel); a DOCKED broke agent that gave up jumping never retries. Fix: after any pass where cached fuel is too low to act AND the worker is idle/stuck at a station, force a `get_status`/`get_ship` refresh; more generally, re-fetch ship state each pass so external fuel/cargo changes (rescue, gifts) are picked up. Operationally: fighter-4 removed from mission-learn fleet 2026-07-19 for manual operator rescue (fleet restarted at 40). Also note: assist only spared **+77** of the requested 180 (its own fuel budget after a 3-jump approach) — RescueFuel sizing should account for the assister's round-trip burn, or top up in the strandee's own tank to a usable threshold.

**⭐🔴 2026-07-27 (operator hunch, CONFIRMED in code, NOT YET FIXED): rescue fuel sizing uses a FLAT 5 fuel/jump and the real rate is hull-dependent.** `pkg/rescue/enrich.go` hardcodes `FuelPerJump = 5`, used two ways: `TransferQuantity` reserves `5*hopsHome + 5` for the RESCUER's trip home before deciding what it can spare (called from `assist.go` `rescueFuelQty`), and `fuelForHops`/`FuelForSystem` sizes the strandee's need at enqueue time. The game's actual jump burn is **`ceil(scale^1.5 × speed × 10 × 0.10)`** (spacemolt.com/docs/guides/fuel) — 1 for a scale-1/speed-1 hull, ~16 for scale 3/speed 3, ~68 for scale 5/speed 6. So the flat 5 **under-reserves badly for any large rescuer** (a scale-3 rescuer 6 hops from home reserves 35 where it needs ~101 → it gives the fuel away and strands ITSELF, creating the next rescue) and over-reserves for a tiny one (transfers less than it safely could — cf. the 2026-07-19 note above where assist spared only +77 of 180). Fix: pass a real per-jump rate into `TransferQuantity` instead of the constant; `haulFuelPerJump` (pkg/worker/haul_fuel.go) already does this correctly and **prefers the SERVER's own `fuel_per_jump` from a `find_route` probe**, falling back to the class formula — reuse it rather than recomputing. Same fix pattern as the mission gate's flat `missionTicksPerJump = 12` → `max(1, 7 - speed)` (shipped `29399a4`): flat per-jump constants in this codebase are hull-blind and all of them are wrong. **⭐✅ FIXED 2026-07-29 (`00d3f62`) — bugs #1, half of #2, the flat fuel rate, and a stale fuel cache.** Details in the numbered list; what shipped:
- `failed` now RE-QUEUES to a different assister. `Record.FailedBy` bars the agent that just failed (so it cannot instantly re-win the election it is usually rank 0 for) and `Record.Attempts` bounds it; only at `RescueMaxAttempts`=5 does it go terminal, with a once-per-agent `rescue: ALERT ... UNRESCUABLE` line from `pollRescues`. The bar expires after `rescueRetryAfter` — with fewer live assisters than the attempt cap, a permanent bar would leave a record unclaimable by everyone AND never escalated.
- `Record.PendingSince`, re-stamped inside `Queue.Transition` on every entry into pending, is what the takeover ladder now measures (falls back to `RequestedAt` for old records).
- `TransferQuantity` takes the measured per-jump rate from `haulFuelPerJump`.
- `RefuelAndSync` (pkg/worker/refuel_sync.go) refuels then re-reads state; wired into assist + shuttle.

**⭐ 2026-07-29 — bug #1 bit again, and RE-ARMING beats deleting.** random-1 (sol, fuel 1/150) and random-9 (nexus_prime, fuel 0/100) sat quarantined 1–2 days, both `status=failed`, both `claimed_by=assist-nexus`, both erroring `no_refueling_pump` — the pump gap ([[project_assist_fleet_refueling_pump_gap]]) created the failure and bug #1 made it permanent. The closed loop: quarantined → no process → no rescue retry → still quarantined.

Diagnostic tell, same as the 2026-07-17 repeat: the worker shows **`0.0% no restarts=0`** in every fleet-status table with **no spawn/connect lines at all**, and greping the overmind log for the agent yields only `send drain to X: worker "X" not connected` plus, at each boot, **`rescue: X restored to quarantine at boot (... status failed)`**. That last line is the confirmation — don't restart the fleet, it will never help.

**Remedy — re-arm `failed` → `pending` instead of deleting the record.** Deleting takes the "no record for quarantined X; releasing" path, which frees the worker *without giving it fuel* — fine only when the strandee is actually fine (cf. salvager-3). Re-arming makes the rescue really happen, and `pollRescues` then releases quarantine on `StatusDone` by itself. Only `pkg/worker/assist.go` `claimNearestPending` consumes records, and it needs `status == pending`, so flip status, blank `claimed_by` and `error`, **and reset `requested_at`** (see the age caveat below). Honour the queue's own protocol: `flock` on `rescue-queue.json.lock` (LOCK_EX) → rewrite → temp-file + `os.Rename`. Both records were claimed within 12s of the rewrite.

**🔴 Reset `requested_at` when re-arming, or you get worst-case routing.** `assistElect` gates on `age >= rank*assistTakeoverInterval` with age from `requested_at`, so a days-old record passes every assister's gate at every rank and nearest-home ranking is fully defeated — first poller wins. Here that sent **assist-frontier (Starfall) to a Sol rescue** and **assist-krynn (Krynn) to a Nexus Prime rescue**, each skipping the assister living in that system. This is bug #2 (distance-blind claiming) with a second, separate mechanism: even once ranking is fixed, stale age still overrides it.

**⭐🔴 2026-07-29 — THE STALE-POI TRAP IS THE #1 TIME-WASTER; IT COST FOUR FAILED RESCUES ON ONE RECORD.** random-9's record said `nexus_prime/null_matter_anomaly`. The strandee was actually **DOCKED at `the_core` with 100,001 credits** and had been since some point after the record was filed on 07-28. Nothing in the pipeline re-reads the target's position, so every assister navigated to the stale POI and failed — and the local one *swapped places with the strandee*, ending up adrift at the asteroid belt while random-9 sat at the station. Four wasted attempts: assist-krynn (20 jumps, "nothing to spare after home reserve"), assist-haven (died at jump 3/21), assist-nexus twice. The tell is `different_location: You are not at the same location as X (they are at <SOMEWHERE ELSE>)` — that error names the true position, so **read it and stop retrying.** Identical to the salvager-3 lesson; it has now bitten twice, so **re-read the strandee's live position before dispatching anyone** and re-verify the POI on each claim, not just at enqueue.

**The actual fix took one command.** `refuel` on random-9 → `Refueled at station. 100 units for 400 credits`, and it had 100k credits the whole time. It was never short of fuel money — it was short of a *process*, because quarantine leaves the worker unspawned and therefore unable to refuel itself. **So check whether the strandee is DOCKED with credits before treating anything as a fuel-transfer problem: if so, release it (or refuel it by hand) and skip the rescue entirely.** Since a hand-fixed record has no assister owed anything, archive it with `status=done` and **`claimed_by` blanked** — `pollRescues` charges the rescue fee only when `ClaimedBy != "" && RescueFuel > 0`, so leaving the stale claimant in place would bill the strandee for a rescue nobody performed. Both random-1 and random-9 ended healthy (fuel 138/150 and 100/100).

**In-system travel is expensive — a 95-fuel hull cannot do one intra-system rescue round trip.** assist-nexus went `the_core` → `null_matter_anomaly` → back and burned **93 of 95 fuel**, arriving home on fumes. Rescue-fuel sizing counts JUMPS and charges nothing for the POI hop at each end, which is badly wrong for a belt/cloud target. Independent support for the Tanker migration in [[project_assist_fleet_refueling_pump_gap]].

**Manual remediation playbook (proven):** quarantined = no process, safe to play_as. `printf 'autopilot <system> <poi>\ndock\nexit\n' | go run ./cmd/tools/play_as <agent>`; then delete the agent's record from data/overmind/rescue-queue.json (under flock on rescue-queue.json.lock) → overmind's next poll logs "no record for quarantined X; releasing" and relaunches.

**Pirate-stronghold strands fail ALL rescuers BY DESIGN (2026-08-14, explorer-1 @ Xamidimura).**
A strand at a pirate stronghold puts the record at `status=failed` with every assist worker in
`failed_by`, because the stronghold refuses the assists' dock — that is station access, not a
pipeline bug, and no retry will ever succeed. Resolution is manual: the strandee itself may have
stronghold access (play_as it out), or clear the record to release the quarantine.

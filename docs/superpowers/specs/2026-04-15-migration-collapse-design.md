# SQLite Migration Collapse Design

**Date:** 2026-04-15
**Status:** Approved

## Goal

Collapse the existing 30 `pkg/knowledge` SQLite migrations into a single
initial-schema migration so every fresh database (notably: every
`TestSQLiteKB_*` test) runs one migration instead of thirty. This is a
performance fix. The target is to bring the `pkg/knowledge` test suite
under `go test -race -count=1 -timeout=120s` comfortably.

## Background

- `pkg/knowledge/sqlite_migrations.go` has 30 migration entries (versions
  1, 2, 3, 5, 6, ... 30 — version 4 was skipped at some point and has
  never existed in the Go source).
- `runMigrations()` at `sqlite_migrations.go:1030` iterates those entries
  and, for each with `m.version > currentVersion`, runs the SQL in its own
  transaction and appends a row to `schema_migrations`.
- There are 74 `TestSQLiteKB_*` tests. Each creates a fresh SQLite file
  via `newTestSQLiteKB` in `sqlite_test.go`, which runs all 30 migrations.
  Under `-race`, `modernc.org/sqlite` is ~10–20× slower than without it,
  so each test pays ~1.5s in migration overhead. Total: ~112s, right at
  the pre-commit hook's 120s `-timeout` ceiling. The mission catalog PR
  tripped this by adding three more SQLite tests.
- `scripts/sql/initialize_database.sql` was just regenerated
  (commit `d7aacf8`) to reflect schema version 30 via
  `scripts/sql/regenerate_initialize_database.sh`. That script runs the
  migration chain against a fresh DB and dumps its schema.
- The live `data/spacemolt-knowledge.db` is at version 30.
- The repo's worktree-local pre-commit hook was bumped from
  `-timeout=120s` to `-timeout=300s` as a temporary band-aid. Reverting
  that revert is part of this work's exit criteria (but optional).

## Non-goals

- Back-compat for database files older than version 30. Any checkout or
  agent with an older DB rebuilds from scratch.
- Removing `runMigrations`'s `ignoreErrors` branch or deleting the
  orphaned `scripts/sql/migrations/migration_v3_to_v4_police_level.sql`.
  Both are tracked as follow-ups (see end of spec).
- Adding a CI check for `initialize_database.sql` drift. Follow-up.

## Architecture

### Source of truth

`pkg/knowledge/initial_schema.sql` becomes the canonical current schema.
It holds every `CREATE TABLE` and `CREATE INDEX` statement the 30-migration
chain currently produces, in a stable order (alphabetical by name within
tables, then indexes). No `INSERT`s, no schema_migrations seeding — the
runner handles that via its own INSERT at `sqlite_migrations.go:1078`.

### Runner changes

`pkg/knowledge/sqlite_migrations.go` shrinks from ~1100 lines to ~80:

```go
package knowledge

import (
	_ "embed"
	"database/sql"
	"fmt"

	_ "modernc.org/sqlite"
)

type Migration struct {
	version      int
	name         string
	sql          string
	ignoreErrors bool
}

//go:embed initial_schema.sql
var initialSchemaSQL string

func migrations() []Migration {
	return []Migration{
		{
			version: 1,
			name:    "initial_schema",
			sql:     initialSchemaSQL,
		},
	}
}

// runMigrations unchanged from its current body (lines 1030–1100).
```

`runMigrations()` itself does not change. Its
`if m.version <= currentVersion { continue }` gate at line 1051 already
handles both relevant cases:

- **Fresh DB:** `currentVersion = 0`, the collapsed v1 runs, and its
  `INSERT INTO schema_migrations` records version 1.
- **Live DB at v30:** `currentVersion = 30`, the collapsed v1 is skipped
  (since 1 ≤ 30). The stale row-for-row schema_migrations entries
  (versions 1, 2, 3, 5, ... 30) are left untouched.

### Generated file

`scripts/sql/initialize_database.sql` is still generated by
`scripts/sql/regenerate_initialize_database.sh`, unchanged. The script
opens a fresh DB, calls `NewSQLiteKB`, and dumps the resulting schema —
it doesn't care whether the runner ran 1 migration or 30 to produce it.
Post-collapse the output should be byte-identical to the pre-collapse
version modulo the `Last Regenerated` header date.

### How `initial_schema.sql` is produced

One-shot helper at collapse time. The regenerate script is already 95%
of the needed logic — it builds a fresh DB and has `sqlite3` dump
`sqlite_master`. For this change the author will:

1. Run the existing regenerate script against the current (pre-collapse)
   main to capture the canonical schema output.
2. Strip the header comment and the `INSERT OR IGNORE INTO
   schema_migrations` block from the bottom (that's runner territory).
3. Keep only the `CREATE TABLE ... ;` and `CREATE INDEX ... ;`
   statements, ordered alphabetically (tables first, then indexes).
4. Save that as `pkg/knowledge/initial_schema.sql`.

No new Go helper is needed long-term; this is a one-time extraction.
After the collapse, if someone wants to edit the initial schema
(rare — future changes should go in new v2+ migrations), they do it by
hand in the `.sql` file.

## Verification (exit criteria)

Two checks, each gates the merge:

### 1. Round-trip — `initialize_database.sql` byte-identical

`scripts/sql/initialize_database.sql` is the canonical schema dump: it's
generated by running all migrations against a fresh DB and dumping
`sqlite_master`. Since both the pre-collapse 30-migration chain and the
post-collapse 1-migration chain must produce the same schema, they must
also produce the same dump file modulo the `Last Regenerated` header date.

```bash
# Pre-collapse: capture the committed canonical file as the reference.
# (main is at d7aacf8 which already has the freshly-regenerated file.)
git show main:scripts/sql/initialize_database.sql > /tmp/before.sql

# Post-collapse: regenerate and compare.
./scripts/sql/regenerate_initialize_database.sh
# Strip the "Last Regenerated: YYYY-MM-DD" line from both to ignore
# cosmetic date differences.
diff \
  <(grep -v '^-- Last Regenerated:' /tmp/before.sql) \
  <(grep -v '^-- Last Regenerated:' scripts/sql/initialize_database.sql)
# Expected: empty output.
```

Zero tolerance for diff. If there's any drift, the collapsed
`initial_schema.sql` is wrong and must be fixed before the collapse
lands.

### 2. Live DB unchanged on startup

Back up `data/spacemolt-knowledge.db`, start `spacemolt-server` briefly,
confirm:

- It starts without errors.
- `SELECT MAX(version) FROM schema_migrations` still returns 30 (no
  new row was inserted).
- `SELECT sql FROM sqlite_master WHERE name='pois'` is unchanged.

Restore the backup afterwards. This verifies the "skip already-applied"
path on real production data.

## Testing

No new tests. The existing 74 `TestSQLiteKB_*` tests continue to
exercise fresh-DB creation via `newTestSQLiteKB`; they should pass
without modification.

### Speedup benchmark

Before the collapse, record:

```bash
time go test -race -count=1 -timeout=300s ./pkg/knowledge/
```

After the collapse, re-record with the same command. Expected delta:
total runtime drops from ~112s to ~30–50s. If we don't see meaningful
improvement, the collapse didn't actually eliminate the per-test
migration overhead and we need to investigate before merging.

### Hook timeout revert (optional, same PR)

Once the benchmark confirms the suite is comfortably under 90s, revert
the local `.git/hooks/pre-commit` `-timeout=300s` back to `-timeout=120s`.
That hook is worktree-local and not tracked; this is just good hygiene,
not a code change.

## Risks

- **Migration 30 (mission catalog) just merged.** The collapsed
  `initial_schema.sql` must include `mission_templates`,
  `mission_objectives`, and `mission_template_locations`. Verification
  step 1 catches omission.
- **Someone adds a migration concurrent with this work.** If a new
  migration lands on main between the pre-collapse schema snapshot and
  the collapse commit, verification step 1 fails. Mitigation: hold the
  rebase short, check main is at the expected HEAD right before
  generating `initial_schema.sql`.
- **Rollback is trivial.** The PR touches two files:
  `pkg/knowledge/sqlite_migrations.go` (shrunk) and
  `pkg/knowledge/initial_schema.sql` (new). Reverting the merge commit
  restores the 30-migration chain instantly. Existing DBs are unaffected
  either way.
- **`base_market` live-DB drift** (flagged in commit `d7aacf8`'s message
  — live has `DEFAULT 0`, current migration DDL has `NOT NULL`/`DEFAULT 1`)
  is pre-existing and orthogonal. The collapse doesn't make it worse.
